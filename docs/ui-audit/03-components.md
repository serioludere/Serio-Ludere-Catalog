## Dimension C — Component inventory and state coverage

**Scope covered.** All 51 `.astro` components on disk, read in full: `src/components/*.astro` (14, not 18 — the brief's count predates the staged deletion of `customer/Gate.astro`), `src/components/admin/*.astro` (6), `src/components/customer/*.astro` (10), `src/components/ui/*.astro` (21). Every state claim below was confirmed with a fresh `grep -n` against the working tree immediately before it was written.

**Counts.** 51 components · 27 interactive · 18 findings (1 P0, 7 P1, 10 P2) · 3 genuinely unreferenced components, of which **1 is unguarded dead code** · 7 duplication pairs, of which **only 1 can safely merge**.

**The single worst problem — C-01.** `ui/Tag.astro` accepts a `pressed` prop, renders it into `aria-pressed`, and never renders it visually. `Tag.astro:23` builds the class list from `style` alone; no `.tag[aria-pressed='true']` rule exists in any of the ten sheets. The drawn pressed look — `.tag--selected`, `components.css:179` — is reachable only through a _different_ prop. A pressed filter chip is pixel-identical to an unpressed one. It is P0 rather than P1 because the state is not merely unstyled, it is claimed in the public API and silently discarded; and because Tag has zero consumers today, it is also the cheapest thing in this report to fix.

**The pattern behind the P1s.** Admin has the states nobody can see and lacks the states everyone needs. `button.go` — the button behind Fetch, Add to sheet, Save, Archive — has `:disabled` and nothing else (`admin.css:138`/`153`), while `admin.css:668` declares a transition for a hover colour that was written and lost. The `Button` component's `loading` prop renders `cursor: progress` and a word (`controls.css:151`); the sheet admits the gap in its own comment. `Checkbox`'s `indeterminate` prop writes a `data-` attribute nothing reads, and the mechanism its comment names — an inline pass — is forbidden by the hash CSP, so it can never be completed as written. And there is no skeleton anywhere outside the public catalogue: `.skeleton` (`components.css:256`) has zero consumers, and `motion.css`, which owns the only working one, is loaded by `Layout.astro:15` alone.

**On duplication, the honest answer is mostly "no".** Six of the seven pairs span a fidelity lock — `VoteButtons`/`Reactions`, `Controls`/`PreviewControls`, `Header`/`PreviewHeader`, `Footer`/`PreviewFooter`, `Specs`/`SpecTable`, `RugCard`/`ProductCard` — and merging their markup would move a parity record by definition. What _is_ safely shareable is the contract underneath them: `votes.ts` already drives `VoteButtons` and `Reactions` through one selector while the two components have drifted into different state sets. Exactly one pair can merge outright: `RugCardAdmin` and `RugRow` duplicate four lines of search-haystack construction character-for-character, comment included, and both live in the unlocked realm.

**Dead components.** `ui/ImageGallery`, `ui/Tag`, `ui/ProgressStep`, `ui/SteppedProgress`, `ui/Toast`, `ui/Toggle` are unreferenced but **deliberately so** — each is justified by name in `tests/unit/styles/component-inventory.test.ts:20-40`. Do not delete them; the recon's caution was correct. The real orphan is `customer/CustomerHeader.astro`: zero references anywhere in the repo including tests and docs, **and outside that test's scope**, because it reads `src/components/ui` only (`component-inventory.test.ts:53`). It is also a hazard, not just waste — it imports the _public_ `Controls.astro` into the customer realm.

## 5 · TWO NOTES FOR THE PHASE-2 PLAN

**The `ui/` set was built ahead of its screens, and that is working.** 6 of 21 are unconsumed, every one of them declared. `component-inventory.test.ts` is a genuinely good guardrail — its one flaw is that it watches a single directory. Extending its `readdirSync` to walk `customer/` and `admin/` would have caught C-07 the day it appeared, and costs one line.

**Breakpoints, for the Phase-2 unification.** Component-scoped `@media (max-width: 767px)` blocks live in exactly five files, all customer-realm: `PreviewFooter.astro:33`, `PreviewHeader.astro:79`, `PreviewControls.astro:160`, `PreviewGate.astro:167`, `SpecTable.astro:81`, `TagFilters.astro:97`. All six are already on the token step, so unifying on 767/1023 requires **no change to any component file** — only to `admin.css`, `preview.css` and `components.css`. Adding 320px support, however, will land in these six, because none of them declares anything below 767.
